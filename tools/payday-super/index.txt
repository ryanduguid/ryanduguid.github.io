## Receipt dates and amounts

Since 1 July 2026, super must generally reach the fund within 7 business days of payday. Proof of sending does not prove timely receipt. Check the applicable timing pathway; this is a review aid, not advice.

The current checker requires amount evidence for a timely receipt. A $120 obligation with a timely receipt date but neither matched_amount nor remitted_amount returns UNKNOWN and exit 2. A late receipt without an amount remains LATE, but cannot reduce the shortfall and uses the as-at date for the maximum estimate.

Historical reports may assume full receipt when an amount is missing. Obtain the receipt amount and rerun the current checker before relying on that result.

Release 0.2.3 corrects the Employment Hero import. A row with the Beam status Reconciled is no longer read as sent to the fund: it gets no remitted date and its payday reads as unfunded, with a warning naming the status. No other check changed. Re-run any review made with releases 0.1.3 to 0.2.2 of an Employment Hero export that contains Reconciled rows.

matched_amount is the supplied amount associated with the payday. It takes precedence over remitted_amount, the supplied amount sent. Neither field authenticates a fund record. A remitted amount without fund receipt evidence does not establish receipt.

For the $120 obligation in this example, a timely $60 matched receipt returns UNPAID, not full payment. A timely $120 matched receipt returns ON_TIME only on the supplied facts. Late receipt returns LATE; a receipt date before the remittance date is rejected. Resolve unmatched records and contradictory evidence before relying on any result.

## Workbook versions and limits

Historical workbooks can assume full receipt when a receipt date has no amount and can extrapolate GIC beyond their covered period. The recorded workbook coverage ends on 31 December 2026; a later period must remain Not assessed unless covered rates are supplied. The CLI option --allow-stale-gic is an explicit override, not current-rate evidence. Do not rely on those amounts without checking the workbook’s Review Checks and rate coverage.

The current source workbook withholds rate-dependent totals if any row needs an uncovered rate. A PyPI install does not install the workbook. The 22 September verification record identifies the tested files and hashes. Those checks do not establish parity for every input, option or later workbook. Read Review Checks before using row results; invalid input can leave a displayed verdict while the workbook is BLOCKED.

## Try the CSV without cloning

With uv installed, download the synthetic CSV as timely_remittance_no_receipt.csv. Open a terminal in that folder and run:

```
uvx --from payday-super-checker==0.1.9 payday-super-check timely_remittance_no_receipt.csv --as-at 2026-08-20 --confirm-remittance-only -o payday-report.csv
```

The command downloads the pinned checker from PyPI and writes payday-report.csv, replacing that file if it exists. Open it to find one AT_RISK contribution with due date 2026-08-17. The current release needs Python 3.14 or later and is Apache-2.0.

Check the matching evidence before relying on the exported file. If employee identifiers or pay period columns are missing, the join degrades and which super payment matches which payday can change. The current checker carries structural matching warnings into the report’s caveats column. Keep the console output with a historical report that omits them. Reconcile affected matches before using a verdict; a row labelled ON_TIME is not reliable evidence of the match itself. See Known limitations (PSC-2).

Exit 0 records your remittance-only acknowledgement. It does not establish timely receipt. Omit --confirm-remittance-only to get the same verdict with exit 2 and a request to resolve or acknowledge the evidence gap.

The fixed example above and the recorded public evaluation use release 0.1.3. Follow that evaluation’s revision and commands to reproduce the historical run. This quick trial uses release 0.1.9 and leaves the fund receipt decision with the reviewer.

## Evidence pack workflow

The CLI change combines the existing checker and practitioner checklist in one command. It writes report.csv, practitioner-review.md, exceptions.json and a blank decision-log.md into a new directory.

The pack’s report carries structural matching warnings. Reconcile affected matches before relying on any verdict; keep console warnings with an older pack if its report omits them.

The report omits employee identifiers and input paths. The checklist and exception queue bind to its SHA-256. Every result other than ON_TIME enters the queue; the fictional example above remains AT_RISK and exits 2. A remittance-only acknowledgement does not clear that queue.

A reviewer uses source row references to reconcile the private input, obtains missing receipt evidence and records decisions under applicable APES 110 and TPB obligations. Existing decision logs are preserved by refusing an output directory that already exists. The files remain private workpapers containing dates, amounts and warnings.

The companion MCP tool, build_payday_super_evidence_pack, accepts structured contribution rows and returns the 4 files in memory. It accepts no input or output paths, writes no files and records no decisions. It requires a checker with evidence pack support.

The identifier-free report is for the included checklist. Existing review-pack and PaydaySuper.Report Excel imports require the ordinary checker’s 18-column report.

This workflow is included in the current checker and MCP server. The historical evaluation predates it. Reproduce the recorded development snapshot with fictional data. No advice, lodgement or ledger write is performed.

Alongside the receipt amount limitation, two further limitations are recorded against this tool: an extrapolated general interest charge rate past the end of the published table, and the ways the payroll-to-super join degrades when identifiers do not match. See Known limitations.

Version, file fingerprints and timing boundary

Without a fund receipt date, records cannot prove ON_TIME. Remittance timing can still prove LATE, while timely remittance without fund receipt evidence remains AT_RISK.
