## $35,957.55 profit, yet a $25,160 cash shortfall

Lumbridge Services is a fictional maintenance business in Newcastle, NSW. Moving one $44,000 customer receipt from 14 October to 28 November 2026 leaves quarterly profit before income tax unchanged at $35,957.55 while the daily cash balance falls to −$25,160.00 on 6 November. All amounts are AUD and every figure is fictional.

December closing cash | $67,320.00 | $67,320.00

# Workpaper Review Gate evaluation

Result: release v0.1.3 of the Workpaper Review Gate stops the incomplete fictional BAS pack with NOT_READY and passes the corrected pack as READY. Reproduce both runs below; a manager still decides whether the work may progress.

Published 26 August 2026. Last reviewed 30 September 2026. Newer releases exist; the Workpaper Review Gate page names the current one.

## Accounting problem

Before manager review, the preparer needs repeatable checks for completeness and unresolved blocking items against the configured rules.

## Fictional inputs

The evaluation uses the repository fixtures examples/bas-not-ready and examples/bas-ready. They contain no client data.

## Expected result

These results describe readiness for review; a manager still decides whether work may progress.

Pack | Released expectation
Incomplete BAS | Exit 2 with NOT_READY.
Corrected BAS | Exit 0 with READY and no configured findings.

## Controls triggered

- MISSING_ARTEFACT for gst_control_gl
- SELF_REVIEW_INCOMPLETE
- OPEN_ITEM_BLOCKING

## Human decision

READY means no configured gate tripped; it is not approval, advice or lodgement authority.

A manager still judges correctness, risk, materiality, client impact and whether the pack may progress.

## Reproduce

```
git clone --branch review-ready-gate/v0.1.3 --depth 1 https://github.com/ryanduguid/accounting-review-pipeline.git
cd accounting-review-pipeline/packages/review-ready-gate
uv sync --locked --all-extras
uv run review-ready gate --profile bas --pack examples/bas-not-ready --output outputs/evaluation-not-ready
uv run review-ready gate --profile bas --pack examples/bas-ready --output outputs/evaluation-ready
uv run pytest tests/test_evaluation_pack.py -q
```

# Xero trial balance integrity evaluation

Source: https://duguid.com.au/evaluate/xero-trial-balance-integrity/

# Xero trial balance integrity evaluation

Result: of 3 fictional CSV fixtures, the balanced file exports and the movement and year-to-date failures stop with nothing written. Reproduce the offline integrity gate below, then inspect the human review boundary.

Published 26 August 2026. Last reviewed 30 September 2026. Newer releases exist; the Xero trial balance export page names the current one.

Problem

An automated trial balance export can look tidy while one balance pair is wrong.

Control

Check movement and year-to-date debits against credits before any CSV write.

Evidence

Three fictional fixtures isolate a passing file, a movement failure and a YTD failure.

Result

One run exits 0. Two runs exit 1 and report that nothing was written.

Limit

Balance does not prove completeness, classification or approval.

## Accounting problem

Xero’s Trial Balance endpoint returns current month movement and year-to-date values. Before any CSV write, the exporter independently checks both debit and credit pairs, so an imbalance in either pair stops the export.

The production tool reads trial balance data directly from Xero’s Accounting API Reports endpoint.

## Intended reviewer

This pack is for a reviewer who wants to reproduce the offline integrity gate without connecting to Xero or handling client data.

## Fictional inputs

The 3 CSV files are fictional output-shape fixtures. They are not Xero API responses or client records, and no OAuth flow runs in this evaluation. No Xero tenant credentials or tenant data are used.

## Reproduce

Needs Git and Python 3.10 or newer with pip; the commands are the same on Windows, macOS and Linux. Clone the Accounting Review Pipeline at tag xero-trial-balance-export/v0.1.6 (commit 3ae854911bf36f00bd3cc3eeafd1855848896629) and run these commands from packages/xero-trial-balance-export. Dependency installation may download the hash-locked packages. Once dependencies are installed, the 3 evaluation runner commands are fully offline, make no network request and write no output file.

```
git clone --branch xero-trial-balance-export/v0.1.6 --depth 1 https://github.com/ryanduguid/accounting-review-pipeline.git
cd accounting-review-pipeline/packages/xero-trial-balance-export
python -m pip install --require-hashes -r requirements.lock
python -B -m unittest tests.test_evaluation_pack -v
python -B -m unittest discover -s tests -v
python evaluation/xero_tb_integrity/run.py ../../contracts/xero-trial-balance-v1/fixtures/passing.csv
python evaluation/xero_tb_integrity/run.py ../../contracts/xero-trial-balance-v1/fixtures/failing_movement.csv
python evaluation/xero_tb_integrity/run.py ../../contracts/xero-trial-balance-v1/fixtures/failing_ytd.csv
```

## Expected result

Fictional fixture | Expected result
passing.csv | passing.csv exits 0 and reports that movement and YTD balance.
failing_movement.csv | failing_movement.csv exits 1, identifies the movement pair and reports Nothing written.
failing_ytd.csv | failing_ytd.csv exits 1, identifies the YTD pair and reports Nothing written.

## Controls triggered

- failing_movement.csv breaks only the current month Debit/Credit pair.
- failing_ytd.csv breaks only the YTDDebit/YTDCredit pair.
- The evaluation runner calls the production check_balanced gate before any CSV write.

## Primary sources

- Xero, Accounting API Reports
- Xero, OAuth scopes

## Versions

Product release v0.1.6; fixture version 1; source reviewed 2026-08-26.

xero-trial-balance-export/v0.1.6 is the first monorepo release to contain this evaluation and the shared contract it exercises. The export behaviour is unchanged from v0.1.4, and the evaluation artefacts are fixed to that release’s commit.

## Human decision

A balanced export passes this integrity control only; a human still decides completeness, classification, accounting treatment and fitness for review.

The integrity result does not approve the export or replace professional review.

# Payday Super timing evidence evaluation

Source: https://duguid.com.au/evaluate/payday-super-evidence/

# Payday Super timing evidence evaluation

Result: the 4 fictional fixtures return AT_RISK for a timely remittance with no fund receipt, LATE for a late remittance or a late receipt, and ON_TIME only for a receipt on the due date. Reproduce them below, then inspect what remittance evidence cannot establish.

Published 26 August 2026. Last reviewed 30 September 2026. This review puts the recorded result first. The recorded evaluation and its release pins are unchanged. Newer releases exist; the Payday Super page names the current one.

## Accounting problem

For Payday Super, the operational record can show when money was remitted, but the statutory timing question depends on when an eligible fund received and allocated the contribution.

## Intended reviewer

This pack is for an accountant, payroll reviewer or technical evaluator who wants to reproduce the evidence classifications without handling a client payroll export.

## Fictional inputs

The 4 CSV fixtures contain fictional dates and amounts for a supported due date of 17 August 2026 and an as-at date of 20 August 2026. No client, employee or live payroll data is included.

## Reproduce

This historical run remains pinned to 0.1.3. Checker 0.1.6 treats a receipt date without an amount as full receipt, with a caveat. Published 0.1.7 corrects that assumption. Check the version-specific receipt rules; these historical outputs do not establish a fix.

Needs Git, and uv with Python 3.12; the commands are the same on Windows, macOS and Linux. Clone the australian-accounting monorepo at tag payday-super-checker/v0.1.3 (commit 8e9bd7235030b2c42bc8f2e7d2e8a60dce627182) and run these commands from packages/payday-super-checker. The first 4 commands write the 4 reports; the final command runs the evaluation contract test.

```
git clone --branch payday-super-checker/v0.1.3 --depth 1 https://github.com/ryanduguid/australian-accounting.git
cd australian-accounting/packages/payday-super-checker
uv run --locked --extra dev --python 3.12 payday-super-check evaluation/payday_super_evidence/fixtures/timely_remittance_no_receipt.csv --as-at 2026-08-20 -o timely-report.csv
uv run --locked --extra dev --python 3.12 payday-super-check evaluation/payday_super_evidence/fixtures/late_remittance_no_receipt.csv --as-at 2026-08-20 -o late-remittance-report.csv
uv run --locked --extra dev --python 3.12 payday-super-check evaluation/payday_super_evidence/fixtures/receipt_on_due_date.csv --as-at 2026-08-20 -o on-time-report.csv
uv run --locked --extra dev --python 3.12 payday-super-check evaluation/payday_super_evidence/fixtures/receipt_after_due_date.csv --as-at 2026-08-20 -o late-receipt-report.csv
uv run --locked --extra dev --python 3.12 pytest tests/test_evaluation_pack.py -q
```

## Recorded development evidence pack

The tool page describes the workflow introduced in checker 0.1.4 and MCP 0.2.2. These commands preserve the original development snapshot for comparison. From the monorepo root, fetch CLI PR 147 and select the exact development revision below before entering the checker directory. The published v0.1.3 checkout used above does not contain this command.

```
git fetch origin pull/147/head
git switch --detach d91bef569e01c8b9e4f15bbe0978f33bf4567a8b
cd packages/payday-super-checker
uv run --locked payday-super-check evidence-pack evaluation/payday_super_evidence/fixtures/timely_remittance_no_receipt.csv --as-at 2026-08-20 -o evidence-pack
uv run --locked --extra dev pytest tests/test_evidence_pack.py -q
```

The evidence pack command exits 2 and writes 4 files into a new directory. exceptions.json must contain AT_RISK; decision-log.md has blank evidence, decision and sign-off sections. Tests verify deterministic output, identifier omission, SHA-256 binding, existing-directory refusal and the 4 pinned timing outcomes. They do not establish model performance or renew the legal review date.

The new command follows review-pack exit meanings: 0 only for all ON_TIME, 2 for any exception and 1 on input or write failure. The existing checker command retains its remittance-confirmation behaviour. Missing fund receipt evidence is never inferred.

## Expected result

Fictional fixture | Expected result
timely_remittance_no_receipt.csv | timely_remittance_no_receipt.csv exits 2 with AT_RISK.
late_remittance_no_receipt.csv | late_remittance_no_receipt.csv exits 2 with LATE.
receipt_on_due_date.csv | receipt_on_due_date.csv exits 0 with ON_TIME.
receipt_after_due_date.csv | receipt_after_due_date.csv exits 2 with LATE.

A missing receipt cannot prove on-time, remittance timing can prove late and timely remittance without receipt remains at-risk. The outcome identifiers are AT_RISK, ON_TIME and LATE.

## Controls triggered

The production check keeps a missing receipt at AT_RISK, records an on-time receipt as ON_TIME and classifies a remittance after the deadline or a late receipt as LATE.
